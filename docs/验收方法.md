# 端到端验收方法

> 记录本项目「怎么验证」的实操细节，以及三个**极具误导性**的现象。
> 所有结论来自 2026-09 本机实测。

## 一、跑验收脚本的正确姿势

```bash
cd ienglish

# 1) Playwright 装在 Node 隔离工作区，必须指路
export NODE_PATH="C:/Users/lenovo/.workbuddy-ai/binaries/node/workspace/node_modules"

# 2) 本机代理会拦外网请求（LLM 调用需要直连）
unset http_proxy https_proxy ALL_PROXY HTTP_PROXY HTTPS_PROXY

# 3) 起 dev server（用 run_in_background，不要用 (cmd &) 子 shell）
NEXT_DIST_DIR=.nextdev6 npx next dev -p 3011

# 4) 签发登录 token（下节）
TOK=$(node scripts/mint-token.mjs)

# 5) 跑验收
BASE=http://127.0.0.1:3011 IE_AUTH="$TOK" node scripts/verify-game-ui.cjs
```

浏览器必须是 **Edge**（`channel: 'msedge'`）—— 本机 Chrome 渲染进程会崩。

## 二、★★ 误区一：鉴权开启后不带 Cookie 跑验收

**现象**：页面一切正常 —— 5 张场景卡都在、立绘加载成功、关卡图标 4/4、
开场白正确。但**每一轮进度条都停在 0/4**，跑满 8 轮也不结算。

**直觉判断**：关卡推进逻辑坏了。

**真相**：`/api/chat` 返回 **401**。因为 `/admin` 里启用了访问口令，
所有对话请求被挡下，AI 从未回复，进度自然不动。

这个现象之所以危险，是因为「结构与美术全部正常」会让人排除掉鉴权方向，
转而怀疑进度计算代码。**排查时要先确认接口状态码，再看界面。**

### 签发 token

server 与本地共享同一个 `SETTINGS_SECRET`，所以可以本地签一个合法 token：

```js
// scripts/mint-token.mjs
import crypto from 'node:crypto';
import fs from 'node:fs';

const secret = (fs.readFileSync('.env.local','utf8').match(/^SETTINGS_SECRET=(.*)$/m)||[])[1]?.trim();
const key = crypto.scryptSync(secret, 'ienglish-auth-v1', 32);   // 盐必须与 lib/auth.js 一致
const b64url = (b) => Buffer.from(b).toString('base64')
  .replace(/\+/g,'-').replace(/\//g,'_').replace(/=+$/,'');

const body = {
  role: 'admin',
  iat: Math.floor(Date.now()/1000),
  exp: Math.floor(Date.now()/1000) + 86400*14,
};
const data = b64url(JSON.stringify(body));
const sig  = b64url(crypto.createHmac('sha256', key).update(data).digest());
console.log(`${data}.${sig}`);
```

**关键点**：`scryptSync(secret, 'ienglish-auth-v1', 32)` 里的盐串必须和
`lib/auth.js` 的 `signingKey()` 完全一致，否则签名对不上。

拿到 token 后分别用两种方式注入：

- **直连接口测试**：`Cookie: ie_auth=<TOK>` 请求头
- **Playwright**：`ctx.addCookies([{ name:'ie_auth', value: TOK, domain, path:'/', httpOnly:true }])`
  （脚本已支持，传 `IE_AUTH` 环境变量即可）

## 三、★★ 误区二：用 UI 自动化测首字延迟

同一个指标，两种测法差 5000 倍：

| 测法 | 首字延迟 | 可信度 |
| --- | --- | --- |
| 直连路由（Node 消费自家 `/api/chat`） | **0–1 ms** | ✅ 真实值 |
| Playwright 轮询 `.caret` 出现 | **5041–11353 ms** | ❌ 假的 |

**原因**：Playwright 每轮 `page.locator().count()` 本身耗时 100ms+，
叠加冷启动与轮询间隔，把真实的首字延迟完全淹没了。

**结论**：首字延迟**必须直连路由测**。验收脚本里的 TTFT 数字只能当
「流式确实生效了」的存在性检查，不能当性能数值看。

## 四、★★ 误区三：等回复用固定 sleep 或只看 `.typing`

改成流式后，`waitReply()` 的判据必须同步升级：

- **首字到达即撤掉 `.typing` 气泡** → 只看 `.typing` 会**提前误判为结束**，
  读到半截回复。
- **流式收尾期间 `.caret` 光标还在** → 需要它来判断「还在写」。

正确判据（三者同时满足）：

```js
const typing = await page.locator('.typing').count();
const caret  = await page.locator('.caret').count();
const busy   = await page.locator('button.send').isDisabled();
if (typing === 0 && caret === 0 && !busy) { /* 回复结束 */ }
```

另外**不要用固定 `sleep(5000)`** 代替轮询 —— 快的时候浪费 4 秒，
慢的时候直接读到半截。用轮询 + 超时上限（本项目用 60s）。

## 五、图片「存在」≠「加载成功」

验证美术资源时，**不能只看 DOM 里有没有 `<img>`** ——
404 的图片元素依然存在于 DOM 中。必须查浏览器是否真的加载成功：

```js
const loaded = await locator.first().evaluate((el) => el.complete && el.naturalWidth > 0);
```

`naturalWidth > 0` 才算真的渲染出来了。这能抓到两类问题：
文件缺失（404），以及文件损坏（如上游返回错误文本被当成图片落盘）。

## 六、本机 `next build` 不可用（与验收无关，但会踩）

本机跑 `npx next build` 会**编译成功、类型检查通过、页面全部生成**，
然后在收尾清理阶段被 safe-delete hook 拦下，报
`[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]`。

**这不是代码问题**，改 `distDir` 也绕不过（它接着删别的）。
→ 本机一律用 `next dev` + curl 测路由状态码。
Vercel 无此 hook，构建正常完成。
