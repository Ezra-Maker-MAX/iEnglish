# 方案 A 技术架构设计
## 基于 Vercel + Turso 的儿童英语学习 AI 硬件

> 版本 v1.0 · 2026-09-28
> 目标硬件：ESP32-S3（小智 xiaozhi-esp32 固件）
> 技术栈：Vercel (Next.js + serverless) + Turso (libSQL/SQLite)

---

## 0. 一个必须先讲的硬约束

**Vercel 无法直接承载 ESP32 的长期 WebSocket 长连接。**

经核实 Vercel 官方文档（2025-11 实时数据指南）：

| 套餐 | WebSocket 连接最大时长 |
|---|---|
| Hobby | **300 秒** |
| Pro | **800 秒**（1800 秒为 beta 上限） |

但 Vercel **原生支持 WebSocket**（public beta，跑在 Fluid compute 上），且：

- 连接**固定**在接收它的实例上，部署后旧连接在旧版本上走完
- 连接达到函数最大时长**必然关闭**，且**没有任何机制能让它超过上限**
- 官方明确说明：**周期性断连是预期行为，不是 bug**

### 这意味着什么

小智设备的对话是「唤醒 → 说话 → 回复」的短会话模式，**单次交互通常 10–60 秒**。所以：

- ✅ **300 秒上限对短会话完全够用** —— 一次问答不会持续 5 分钟
- ✅ Vercel 原生 WebSocket 可以承接设备连接
- ⚠️ 但**必须实现客户端重连**（小智固件本身有重连逻辑，退避策略从 1s 翻倍至 30s）
- ❌ **不能用 Vercel 做「设备永远在线」的常驻网关**

**结论：你的 Vercel + Turso 组合可行，但架构要按「短会话 + 可重连」设计，不能按常驻服务设计。**

### 混合模式的具体边界

| 数据 | 位置 | 理由 |
|---|---|---|
| 原始录音 | **仅设备内存**，用完即弃 | 最敏感，不落库 |
| ASR 转写文本 | 云端 API 处理后存 Turso | 用于家长看对话内容 |
| 对话回复 | 云端 LLM 生成 | 质量优先 |
| 发音评测音频 | 直接送评测 API，**不落库** | 只存评分结果 |
| 学习进度/生词 | Turso | 需要跨设备、可分析 |

> ⚠️ 需要你确认：**ASR 走云端意味着孩子语音会经过服务商**。若这不可接受，ASR 需改本地（见 §6 替代方案）。

## 2. Turso 数据模型

你说「两者都要」——既存学习记录，也存场景配置。以下是完整 schema。

```sql
-- ============ 孩子档案 ============
CREATE TABLE children (
  id            TEXT PRIMARY KEY,          -- uuid
  nickname      TEXT NOT NULL,             -- 昵称（不存真实姓名）
  english_name  TEXT,                      -- 孩子自选的英文名
  grade_band    TEXT,                      -- 'primary_high' | 'junior' | 'senior'
  cefr_level    TEXT DEFAULT 'A1',         -- 评估出的水平
  created_at    INTEGER DEFAULT (unixepoch())
);

-- ============ 设备 ============
CREATE TABLE devices (
  device_id     TEXT PRIMARY KEY,          -- 设备 MAC
  client_id     TEXT,                      -- 固件生成的 UUID
  child_id      TEXT REFERENCES children(id),
  name          TEXT,                      -- "书桌上的小盒子"
  token_hash    TEXT NOT NULL,             -- Bearer token 的哈希
  last_seen_at  INTEGER,
  firmware_ver  TEXT
);

-- ============ 场景配置（可热改，不用烧固件）============
CREATE TABLE scenarios (
  id            TEXT PRIMARY KEY,
  slug          TEXT UNIQUE NOT NULL,      -- 'airport-checkin'
  title         TEXT NOT NULL,             -- '机场值机+过安检'
  difficulty    INTEGER,                   -- 1 | 2 | 3（对应 ⭐⭐）
  grade_band    TEXT,                      -- 适用学段
  roles         TEXT,                      -- JSON: {"student":"Passenger","ai":"Ground staff"}
  vocab_list    TEXT,                      -- JSON: ["boarding pass","carry-on",...]
  system_prompt TEXT NOT NULL,             -- 核心：AI 扮演的提示词
  opening_line  TEXT,                      -- AI 开场白
  stuck_hints   TEXT,                      -- JSON: 卡壳点 → 二选一提示
  upgrade_pairs TEXT,                      -- JSON: [["I want window","I'd prefer a window seat"],...]
  active        INTEGER DEFAULT 1
);

-- ============ 会话 ============
CREATE TABLE sessions (
  id            TEXT PRIMARY KEY,
  child_id      TEXT REFERENCES children(id),
  scenario_id   TEXT REFERENCES scenarios(id),
  started_at    INTEGER,
  ended_at      INTEGER,
  turn_count    INTEGER DEFAULT 0,
  duration_sec  INTEGER,
  completed     INTEGER DEFAULT 0           -- 是否走完场景
);

-- ============ 对话轮次 ============
CREATE TABLE turns (
  id            TEXT PRIMARY KEY,
  session_id    TEXT REFERENCES sessions(id),
  seq           INTEGER NOT NULL,
  role          TEXT NOT NULL,              -- 'child' | 'ai'
  text          TEXT NOT NULL,              -- 转写/生成文本
  asr_conf      REAL,                       -- 识别置信度（用于判断童声识别质量）
  created_at    INTEGER DEFAULT (unixepoch())
);
CREATE INDEX idx_turns_session ON turns(session_id, seq);

-- ============ 生词本 ============
CREATE TABLE vocab_progress (
  id            TEXT PRIMARY KEY,
  child_id      TEXT REFERENCES children(id),
  word          TEXT NOT NULL,
  first_seen_at INTEGER,
  times_seen    INTEGER DEFAULT 1,
  times_used    INTEGER DEFAULT 0,          -- 孩子主动说出过几次
  mastered      INTEGER DEFAULT 0,
  UNIQUE(child_id, word)
);

-- ============ 发音评测记录（只存分数，不存音频）============
CREATE TABLE pron_scores (
  id            TEXT PRIMARY KEY,
  child_id      TEXT REFERENCES children(id),
  session_id    TEXT REFERENCES sessions(id),
  word          TEXT,
  expected_ipa  TEXT,
  heard_ipa     TEXT,
  score         REAL,
  created_at    INTEGER DEFAULT (unixepoch())
);

-- ============ 每日统计（家长端看板用）============
CREATE TABLE daily_stats (
  child_id      TEXT REFERENCES children(id),
  date          TEXT NOT NULL,              -- 'YYYY-MM-DD'
  minutes       REAL DEFAULT 0,
  turns         INTEGER DEFAULT 0,
  scenarios_done INTEGER DEFAULT 0,
  new_words     INTEGER DEFAULT 0,
  PRIMARY KEY (child_id, date)
);
```

### 为什么场景配置放数据库 —— 这是核心设计决策

这是**让 Vercel + Turso 组合真正产生价值的地方**：

- 你要调整 AI 的教学方式 → **改 `scenarios.system_prompt` 一行数据，立即生效**
- 不用重新编译 ESP32 固件、不用重新烧录
- 可以给不同孩子分配不同场景（`grade_band` 过滤）
- 可以 A/B 测试两种提示词的教学效果

传统的「提示词烧进固件」做法，每次改一句话都要走完整烧录流程——这是这类项目最大的迭代瓶颈。

## 3. 关键实现：小智协议的服务器端

小智设备用 **WebSocket 单连接双工**（不是 MQTT+UDP，MQTT 只用于 MCP 的 IoT 通道）。

### 3.1 握手流程（必须严格实现）

```
设备 → 服务器:  WebSocket Upgrade
                 Headers:
                   Authorization: Bearer <token>
                   Protocol-Version: 1
                   Device-Id: <MAC>
                   Client-Id: <UUID>
```

设备随后发 hello：

```json
{
  "type": "hello",
  "version": 1,
  "features": { "mcp": true, "aec": true },
  "transport": "websocket",
  "audio_params": {
    "format": "opus",
    "sample_rate": 16000,
    "channels": 1,
    "frame_duration": 60
  }
}
```

服务器**必须在 10 秒内**回复：

```json
{
  "type": "hello",
  "transport": "websocket",
  "session_id": "<uuid>",
  "audio_params": {
    "format": "opus",
    "sample_rate": 24000,
    "channels": 1,
    "frame_duration": 60
  }
}
```

> ⚠️ `"transport": "websocket"` 缺失 → 设备认为音频通道未打开。这是最常见的踩坑点。

### 3.2 音频规格

| 方向 | 编码 | 采样率 | 声道 | 帧长 |
|---|---|---|---|---|
| 上行（孩子说） | Opus | 16000 Hz | 1 | 60 ms |
| 下行（AI 说） | Opus | 24000 Hz | 1 | 60 ms |

### 3.3 完整交互时序

```
1. 设备 → 服务器   hello{version:1, opus/16000/mono/60ms}
2. 服务器 → 设备   hello{transport:"websocket", session_id, opus/24000}
3. 设备 → 服务器   listen{state:"start", mode:"auto"}
                   + [二进制 Opus 帧 ...]  ← 孩子说话中
4. （VAD 检测到静音结束，聚合音频）
5. 服务器 → ASR    → 得到文本
6. 服务器 → 设备   stt{text:"..."}        ← 可选，用于屏幕显示
7. 服务器 → LLM（注入场景 system prompt + 历史）
8. 服务器 → 设备   tts{state:"start"}     ← ⚠️ 必须先发！
9. 服务器 → 设备   [二进制 Opus 帧 ...]   ← AI 回复音频
10. 服务器 → 设备  tts{state:"stop"}
11. 设备回到 Idle（或自动续听 → Listening）
```

### 3.4 三个高频踩坑点

1. **TTS 前必须先发 `tts{state:"start"}`**
   否则设备仍在 `listening` 状态，二进制音频帧会被**直接丢弃**（设备为避免与麦克风流冲突而丢弃）。

2. **握手 10 秒超时**
   服务器 hello 回复慢了就判定连接失败。冷启动的 serverless 函数要特别注意。

3. **所有消息必须含 `type` 字段**
   缺 `type` 的设备会静默丢弃（日志 `Missing message type`），排查起来很痛苦。

## 4. 分两期落地计划

你选择「两者都要，分期做」——这是正确判断，因为**先验证教学效果，再投硬件**能避免浪费。

### 第一期：Web 端验证（不买硬件，1–2 周）

**目标：验证两件事**
1. 孩子**愿不愿意**跟 AI 说英语
2. ASR 对**你自己孩子的童声**识别率如何（最大未知数）

**技术栈**（全部复用你现有的 Vercel + Turso）：
- Next.js App Router（部署 Vercel）
- 浏览器 `MediaRecorder` → 上传音频 → ASR → LLM → TTS → 播放
- Turso 存会话与进度
- `/dashboard` 家长端

**为什么必须先做这期**：
ESP32 硬件 + AEC + Opus 编解码 + 烧录调试，是**数周工程量**。如果孩子用了三天就不玩了，或者 ASR 根本听不懂童声，这些投入全部作废。Web 端一周就能验证，成本接近零。

**验收标准**（建议量化，避免自我欺骗）：
- 孩子**主动**使用 ≥ 5 次（不是你催的）
- ASR 识别率 ≥ 80%（低于此值教学无法进行）
- 单次对话 ≥ 5 轮（说明有对话意愿）

### 第二期：ESP32 硬件化（验证通过后，3–4 周）

**复用第一期的全部后端**，只增加设备接入层：

1. 采购 ESP32-S3 开发板（**必须支持 AEC**）
2. 烧录 xiaozhi-esp32 固件，指向你的 Vercel WebSocket 端点
3. 在 Vercel 实现 `/xiaozhi` WebSocket handler（握手 + Opus 编解码 + 状态机）
4. 场景 system prompt 复用第一期的 Turso 数据，**零改动**

**架构不变、数据不变、教学逻辑不变** —— 只是把「浏览器」换成「硬件盒子」。这是分两期最大的价值。

## 5. Vercel 侧实现要点

### 5.1 WebSocket handler（关键：运行时长配置）

```js
// app/api/xiaozhi/route.js  （Next.js Route Handler）
export const runtime = 'nodejs';      // WebSocket 需 Node.js runtime，不能用 edge
export const maxDuration = 300;       // Hobby 上限 300s；Pro 可到 800
```

各套餐配置：

| 套餐 | maxDuration 建议 | 说明 |
|---|---|---|
| Hobby | `300` | 单次会话足够 |
| Pro | `800` | 更宽松，减少重连 |

**重连是设计的一部分，不是异常处理**。设备端 xiaozhi 固件自带退避重连（1s→2s→…→30s），服务端只需保证：
- 每次新连接**重新握手**
- `session_id` 重新生成，但 `child_id` 通过 `Device-Id` 关联，学习记录不断

### 5.2 Turso 连接

```js
import { createClient } from '@libsql/client';

const db = createClient({
  url: process.env.TURSO_DATABASE_URL,      // libsql://xxx.turso.io
  authToken: process.env.TURSO_AUTH_TOKEN,
});

// 拉取场景配置（每次会话开始时）
const { rows } = await db.execute({
  sql: `SELECT system_prompt, opening_line, vocab_list
        FROM scenarios
        WHERE slug = ? AND active = 1`,
  args: [scenarioSlug],
});
```

> ⚠️ **服务端用 HTTP 客户端，秒级冷启动问题要注意**。`@libsql/client` 在 serverless 中走 HTTP，不是长连接——这与 WebSocket 场景兼容。

### 5.3 环境变量清单（Vercel 项目设置）

```
TURSO_DATABASE_URL=libsql://xxx.turso.io
TURSO_AUTH_TOKEN=xxx
DEVICE_TOKEN_SECRET=xxx            # 设备 Bearer token 的签名密钥
LLM_API_KEY=xxx                    # DeepSeek / 通义
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-flash
ASR_API_KEY=xxx
TTS_API_KEY=xxx
PRON_API_KEY=xxx                   # 可选，发音评测
```

## 6. 替代方案：如果 ASR 不能走云端

如果你的隐私要求更高，或发现云端 ASR 对童声识别差，**关键改动只在一处**：

```
原：设备 → Vercel → 云端 ASR
改：设备 → 家庭本地服务(Pi) → 本地 ASR → 文本 → Vercel → LLM
```

即：**家里放一台树莓派只做 ASR**（Whisper / Qwen3-ASR），转成文本后把**纯文本**发给 Vercel。这样：

- 原始音频不出家门（最敏感的数据保住了）
- LLM 仍用云端强模型（效果不变）
- Turso 照常存文本记录

代价：多一台常开设备。收益：隐私与效果兼得。

**录音音频在 Vercel 侧的处理原则**：无论哪条路径，**原始音频绝不写入 Turso**。它是二进制大对象，写库会让 Turso 迅速膨胀，且是最敏感数据。

## 7. 成本估算

| 项目 | 预估 | 说明 |
|---|---|---|
| Vercel | ¥0 | Hobby 免费额度足够（但 300s 限制） |
| Turso | ¥0 | 免费额度：500 个库 / 足够个人使用 |
| LLM（DeepSeek） | **约 ¥1–5 / 月** | 按每天 30 分钟对话，deepseek-flash 极便宜 |
| ASR + TTS | **约 ¥10–30 / 月** | 这是主要成本项，语音 API 按分钟计费 |
| ESP32-S3 硬件 | **约 ¥100–180** | 一次性 |

**关键结论：软件运行成本约 ¥15–35/月，硬件约 ¥150 一次性。** 相比商业英语学习产品（动辄年费上千），这个成本结构很有优势。

## 8. 需要你决策的三个问题

1. **ASR/TTS 选哪家？** 这是唯一有持续成本且影响童声识别率的决策。
   - 国内：火山引擎、阿里云、讯飞（中文语境 + 童声优化较好）
   - 国外：OpenAI Whisper + TTS（质量高，但网络与合规要考虑）
   - 建议：**第一期先用便宜方案验证，确认教学有效后再优化**

2. **是否要发音评测？** 需要额外 API，且儿童评测准确率需实测。建议**第一期先不做**，先确认孩子愿意开口。

3. **第一期是否需要多孩子支持？** schema 已支持（`children` 表），但若只有一个孩子，可先简化 UI。
