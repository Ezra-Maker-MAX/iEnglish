# 文本模型选型（推理延迟问题）

> 背景：本项目原先用 `agnes-2.5-flash`。上线前实测发现两个致命问题，
> 本文记录排查过程、实测数据与最终方案。

## 一、问题现象

### 现象 1：偶发空回复
第 7 轮对话 AI 返回空字符串。孩子看到的是一个空气泡。

**根因**：`agnes-2.5-flash` 是**推理模型** —— 它会先产出一大段内部思维链
（`reasoning_content`），再从**剩余**的 token 预算里产出可见回复（`content`）。
`max_tokens = 400` 时，思维链把额度吃光，`content` 就是空串。

**识别标志**：响应体里出现这两个字段就说明是推理模型
```
message.reasoning_content
usage.completion_tokens_details.reasoning_tokens   // 实测 agnes-2.5-flash ≈ 116
```

### 现象 2：首字延迟波动极大
孩子在 **5 秒内**没有回应就会走开。而实测：

| 模型 | 非流式中位 | 流式首字（6 次采样） | reasoning_tokens |
| --- | ---: | --- | ---: |
| `agnes-3.0-flash` | 3413ms | 中位 3554ms / 均值 3843ms / 最快 1902ms / **最慢 6041ms** | **0** |
| `agnes-2.5-flash`（原用） | 4042ms | 中位 3536ms / 均值 4289ms / 最快 1343ms / **最慢 8742ms** | 116 |
| `agnes-2.5-pro` | **150485ms** | — | 67 |
| `agnes-1.5-flash` | HTTP 503 | — | — |

补充观测：
- `agnes-2.5-flash` 6 次采样里**出现 2 次 HTTP 429 限流**，`agnes-3.0-flash` 0 次。
- `agnes-2.5-pro` 单次耗时 150 秒，**完全不可用**。
- `agnes-1.5-flash` 虽然出现在 `/v1/models` 列表里，但调用返回
  `HTTP 503 model_not_found: No available channel` —— **列表里有 ≠ 实际开通**。

## 二、两层解法

用户要求「看手册里有没有模型替换或者别的解决办法」。答案是两层都要做：

### 第 1 层：换模型（模型替换）

**换成 `agnes-3.0-flash`**。理由：

1. **无推理开销**（`reasoning_tokens` 恒为 0）—— 从根上消除了「思维链吃光额度导致空回复」。
2. **最慢值更可控**：6041ms vs 8742ms，尾部风险低 31%。
3. **未触发限流**：6 次采样 0 次 429，而 2.5-flash 有 2 次。
4. 首字中位数两者接近（3554 vs 3536ms），但 3.0-flash 的**分布更紧**。

### 第 2 层：改流式（更重要的解法）

**把非流式改成 SSE 流式**。这是收益最大的一步，因为它改变的是**感知延迟**：

| | 改造前 | 改造后 |
| --- | --- | --- |
| 孩子看到第一个字的等待 | 3.5 – 8.7 秒（等完整回复） | **0 – 1ms**（首字到达即渲染） |
| 之后的表现 | 整段文字一次性蹦出 | 逐词蹦出 + 打字光标闪烁 |

改造后实测（走真实 `/api/chat` 路由，5 次采样）：
```
#1 首字 1ms │ 全文 2611ms
#2 首字 0ms │ 全文 9584ms
#3 首字 0ms │ 全文 5834ms
#4 首字 1ms │ 全文 5520ms
#5 首字 0ms │ 全文 2312ms
```

**注意首字是 0-1ms** —— 这不是模型变快了，而是**首字到达就不再等待**，
最后一段文本仍要 2.3-9.6 秒才收完。但对孩子来说，「Max 正在打字」和
「屏幕一片空白」是天壤之别。

### 第 3 层：兜底（防御性）

即使有上面两层，仍保留三重保护：
1. `max_tokens` 默认 400 → **900**（给推理模型留出思维链空间）
2. 空回复时**翻倍重试一次**
3. 仍为空则返回 `Hmm... let me think! Can you say that again? 😊` —— 绝不让孩子看到空白

## 三、实现说明

### 为什么不透传上游 SSE

`app/api/chat/route.js` 把上游的 OpenAI 兼容 SSE **解析后重新编码**成自己的事件流，
而不是直接透传 `Response`。原因：**落库与轮次判定需要 `usage` / `finish_reason`**，
透传就拿不到了。

自定义协议：
```
{t:'delta', v:'...'}                      增量文本
{t:'meta', sessionId, reply, turn, storyComplete}   结束元数据
{t:'error', v:'...'}                      错误
{t:'done'}                                流结束
```

### 为什么不用 EventSource

前端用 `lib/sse.js` 手写消费（`fetch` + `ReadableStream`），不用 `EventSource`：
1. `EventSource` 只支持 GET，我们需要 POST 带 body（历史记录可能很长）
2. `EventSource` 无法中断（组件卸载时要能停）
3. 我们需要在「首字到达」这一刻就更新 UI

## 五、未决问题

- `agnes-3.0-flash` 的最慢值 6041ms 仍高于理想值。**缓解手段是流式**（首字不再受最慢值影响）。
- 若后续需要更低延迟，可评估 `agnes-2.0-flash`（文档标称 256K 上下文，未实测延迟）。
- 高峰期 429 限流（免费档 30 RPM 公开 / 20 实际可执行）在并发用户多时会成为瓶颈。
  **单孩子使用不受影响**；若开放给多用户需评估升级套餐。
